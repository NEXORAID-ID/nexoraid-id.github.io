# NEXORAID V4 — full-stack foundation
V3 remains the public static storefront. V4 adds a separate Cloudflare Worker and portal with real D1-backed order requests, Discord identity, expiring hashed sessions, customer/worker/management/seller/owner permissions, first-claim order workflow and audit events. Catalog prices are indicative, not payments. No game passwords, OTPs or payment details are collected. Seller has customer-level access until a separate seller workflow is designed. No invoice, payment gateway, AI, R2 or Discord ticket synchronization is claimed.
## Deployment (owner)
1. Create D1 database named nexoraid-v4 in Cloudflare; copy UUID and account ID.
2. Create Discord application, enable OAuth2 and register exactly PUBLIC_ORIGIN/api/auth/callback. PUBLIC_ORIGIN must be the HTTPS Worker URL or configured custom domain with no trailing slash.
3. In repository Settings > Environments create cloudflare-v4. Add variables CLOUDFLARE_ACCOUNT_ID, D1_DATABASE_ID, PUBLIC_ORIGIN, OWNER_DISCORD_ID (your numeric Discord user ID), DISCORD_CLIENT_ID. Add secrets CLOUDFLARE_API_TOKEN (only required Worker/D1 permissions scoped to your account), DISCORD_CLIENT_SECRET. Never commit them. If using a custom domain, configure it in Cloudflare first or after the initial workers.dev deployment, then update origin and redirect URI.
4. Run Actions > Deploy NEXORAID V4 on main. Existing V3 workflow remains unchanged. Open PUBLIC_ORIGIN/portal.html after successful deployment.
5. Log in as owner; team members must sign in once before assigning worker/seller roles. Confirm test orders and permissions before accepting real customer requests.
6. Before production: configure rate limits/Turnstile, retention and backup, approve privacy/refund rules, test real Discord OAuth and D1 concurrency, verify domain routing, run security review. Never publish secrets to chat or source.
## Tests
Root npm test includes V4 API, pricing, authorization and SQLite schema tests. These do not prove live OAuth or D1 behavior. Cloudflare deployment runs on relevant main changes or manual dispatch only when the existing cloudflare-v4 environment has all required configuration; it never changes the V3 GitHub Pages deployment. Environment approval policies remain effective.

## Setup interaktif (rekomendasi awal)
Buka Codespaces pada main, lalu jalankan `bash v4/scripts/setup.sh`. Script menguji source, menggunakan login device resmi Cloudflare, memilih akun, membuat atau memakai kembali D1, melakukan build dan dry-run, memasang secret dalam file sementara mode privat, menjalankan migrasi, deploy, dan smoke check. Anda tetap harus mendaftarkan subdomain workers.dev, mengotorisasi Cloudflare, membuat aplikasi Discord dengan redirect URI yang ditampilkan, serta memasukkan ID dan client secret di terminal sendiri. Jangan bagikan secret ke chat. Script tidak mengatur domain Name.com, tidak mengaktifkan paket berbayar dan tidak mengubah V3. Jalankan ulang jika setup terhenti; database dengan nama sama tidak dihapus. Uji OAuth, role dan order nyata pada staging sebelum mengalihkan pelanggan. Untuk deploy CI berikutnya gunakan workflow manual serta variabel/secret GitHub seperti di atas.

## Recovery after a successful deploy but failed health check
Do not recreate D1 or rotate Discord secrets. Pull main, retain your previously generated config values, rebuild with SITE_URL=PUBLIC_ORIGIN, rerun prepare.mjs, then deploy with the same config. Existing encrypted secrets are preserved by Wrangler. Run PUBLIC_ORIGIN=your-origin node v4/scripts/verify.mjs after deployment. Full real OAuth login and D1 order checks are still required.

## Optional Discord Gateway bridge
The separate Discord.js bot may call /api/bot/orders and its claim/status routes using a dedicated 64-hex-character secret NEXORAID_BOT_API_KEY, Authorization: Bearer ..., x-discord-user-id from the actual interaction, and x-discord-guild-id. Only guild 1487728359482851348 is accepted. Create the secret with a cryptographic random generator, configure it in the Worker dashboard and the bot host; do not use the Discord token as this key. The Worker uses D1 roles, not Discord role names. The key is optional and the bot API fails closed without it. This provides shared website orders, not automatic migration of legacy Discord tickets. Keep legacy data backups. Test with staging users before production.

## Four-role access
One Discord OAuth login selects the effective role on the server. Owner is exclusively OWNER_DISCORD_ID. The owner can assign management, worker (Penjoki), customer, or legacy seller after registration. Management sees all orders and may confirm, progress, complete or cancel orders, but cannot claim worker jobs or change roles. Worker claims available orders and progresses assigned confirmed orders. Customer and legacy seller see only their own orders. Migration 0002 adds a separate management grant table without rebuilding existing users or orders. Apply migrations before deploying. The dashboard shows up to 100 latest permitted orders, not lifetime totals. Role assignment is audited; Discord role names do not automatically grant permissions.

The public storefront now links to the official portal in its main navigation, homepage hero and footer. GitHub Pages deploys the storefront only; the portal requires a separate Cloudflare Worker deployment. For an existing configured Codespace use `bash v4/scripts/redeploy.sh` after pulling main. It reuses the previous generated config, applies pending migrations and preserves existing Worker secrets; it does not create a database or reset roles.

### OAuth troubleshooting
An OAuth token exchange error redirects back to the portal with a fixed safe error category. `OAUTH-CLIENT` means check the application Client ID and OAuth2 Client Secret from the same Discord application (not bot token or public key). In Cloudflare Worker settings update only `DISCORD_CLIENT_SECRET` if needed; never publish it. `OAUTH-GRANT` means restart login, not reload the callback URL. Verify the exact registered redirect URI. Logs contain only upstream HTTP status and a predefined category; do not share callback URLs or tokens. Run the existing redeploy helper to apply source changes.

### Automatic V4 updates
Relevant pushes to main trigger the dedicated Cloudflare workflow. It validates the presence of each required environment variable/secret before any remote migrations or deployment. If credentials are missing, the job fails clearly without touching D1. Use the existing Cloudflare account and database; never paste secrets into source or logs. Existing environment approvals are not bypassed. A successful smoke test verifies routing and login redirect, not an actual authenticated Discord session.

### Branded login entry
Both storefronts now expose login.html, a static branded entry that sends users to the official Worker OAuth endpoint, never collecting credentials. The authenticated Worker portal shares the design. GitHub Pages can publish the login landing independently, but OAuth and role dashboards require the Worker to be deployed and configured. Mobile and desktop smoke tests cover the static login entry and OAuth destination.

OAuth diagnostics now distinguish token and identity transport failures. Token exchange uses the documented unversioned Discord OAuth endpoint and an explicit form-encoded string body, a product User-Agent, a bounded timeout and no automatic redirects. Runtime logs include only the fixed stage, reason, HTTP status, format or exception class; no raw exception text, tokens or codes. A transport failure may still require resolving the upstream network issue. Do not retry a spent authorization code.

## Operations foundation
Migration 0003 adds manually quoted invoices, owner-verified payment records, worker evidence notes and an immutable-by-API completion settlement. Existing completed orders are not backfilled or assumed paid. Management can assign a registered worker before processing, confirm and review evidence; only owner verifies payment. Paid orders cannot be cancelled until a reviewed refund workflow exists. Joki (GTA catalogue except Cherax) uses integer 60/40; other services use a Rp10,000 worker fee; seller has no automatic settlement until its policy is confirmed. Do not treat owner share as net profit. Payment verification is manual, not bank/QRIS integration, and evidence is a text reference, not file upload. Weborder claim/status continues to use shared D1 orders; legacy tickets and settlements remain separate. No automatic migration, payout or real-money transfer is performed. Apply migrations before using the new dashboards.

Additional checks exercise all four role interfaces with fixture API responses and a real SQLite adapter for authorization, state transitions and settlement. A unique payment reference cannot fund two verified invoices. A worker with active assignments cannot be demoted until those assignments are resolved. Discord bridge may submit work evidence under the actual interaction identity; payment confirmation remains owner-only on the web. These tests are not live Discord/D1 production validation.

### Static merchant QRIS
The owner supplied the NEXORAID STORE QRIS (NMID ID1026637062856). The SVG preserves the original 57×57 module matrix, with four-module quiet zone; no payment fields were modified. It is displayed only on the customer's own active quoted invoice (the asset itself is public). Customers enter the invoice amount and verify the merchant in their payment app, then send a receipt via the official Discord ticket. This is static QRIS, not a payment gateway or automatic verification. No QR is shown on paid/cancelled/completed orders. Before going live, owner should scan the asset and verify the merchant through the payment provider.

### Workspace and reports
0005 adds payout reservations and manual owner confirmation, operating expense records, order-specific support cases, payment-reference claims, ratings, availability and pre-work full refund recording. No external money transfer occurs; refunds after work starts or completion remain outside this workflow. Reports use WIB calendar months and distinguish completed settlement margin from cash receipts. Existing historical transactions are not inferred. Support cases are web records, not synchronized Discord tickets. CSV export is the displayed monthly report, not a full database dump. Payout requests reserve the available balance atomically and require an actual owner-confirmed transfer before marking paid.

### Business Center (0006)
Owner can override existing portal service prices, disable services and apply percentage promos. Static public GitHub Pages catalogue remains the source baseline; portal orders and bot order creation use the database override. Supplier deposits/usage/withdrawals are manual ledger records, not actual transfers or operating expense duplication. Investor module supports one active capital tranche and manual distributions from owner-approved realized profit; 25% investor, 5% principal capped at outstanding principal, remainder owner, no new distributions after repayment. The final partial-return surplus is allocated to owner; confirm this policy before real use. Notification center polls scoped audit records every 30 seconds; it is not a push service. Logout-all revokes all web sessions. Business POST rate limits are 120/minute; other routes retain previous controls. No payout, investment acceptance or transfer is initiated by the software.

### Discord ticket links (0007)
Customer can link an active web order using `/weborder ticket id:<order-id>` in the authorized guild. The bot checks ownership before creating/reusing the customer's existing ticket, then registers the channel reference. Links do not synchronize legacy payment, claim or settlement state and are not proof a channel remains open. The dashboard displays the registered channel to customer, assigned worker or staff only. Requires bot bridge configuration and deployment of both repos.

### Integrity gate (0008)
Health now queries required tables and reports schema and deployed Git SHA; a missing DB or OAuth configuration returns degraded HTTP 503. Public Worker API catalog uses overrides (static Pages HTML still baseline). Optional request_id makes order retries idempotent per customer and same service/quantity. Invoice changes are locked after payment report; owner can reject a verified-not-received claim with a retained reason. Former workers retain access to their own settlement and payout records but no worker permissions. Database triggers prevent active-worker demotion races. Rate limiting applies to authenticated POST routes; public OAuth/GET rate limits require separate infrastructure. No money transfers initiated.

### Order collaboration (0009)
Scoped chat and internal notes, staff-assigned priority/deadline, month-filtered deadline list, private payment/work image attachments. Files limited to three per kind/order and 512 KiB each, with PNG/JPEG signature checks; downloaded as octet-stream with attachment headers, not rendered inline. Signature checks are not full malware scanning. Payment proof is visible only to customer and owner; work proof to assigned worker and staff. Do not submit credentials. No attachment automatically verifies payment or completes work. Calendar lists at most 200 items; chats at most 500 per order, showing newest 100. Retention/backup policy and real D1 load testing remain required.

### Live storefront
The public storefront on the official Pages and Worker origins fetches the public catalogue (credentials omitted), merges live prices and excludes disabled services. An offline/baseline notice is visible when the API is unavailable. Built static HTML, CSV and historical SEO metadata remain fallback snapshots; JavaScript replaces the visible price table and download when live data is available. Marketing copy outside catalog cards may still refer to older promotions; use the portal invoice as the final price.
